# Private Mail Engine integration

The Mail Engine runs as its own Compose project (mailcow) in
`/opt/mailcow-dockerized`, separate from MateMail. The files here are the
**only** part of it that MateMail owns, and together they are the entire
two-way path between MateMail and the engine:

- **MateMail → engine** — the HAProxy gateway. Provisioning calls and the
  platform sender's own submission.
- **engine → MateMail** — the SMTP policy bridge (P5). Postfix asking MateMail
  whether a message may be accepted or sent.

They live here so the path is recoverable from this repository. Losing
MateServer must not mean reconstructing them from prose.

| File | Production destination | Mode |
|---|---|---|
| `docker-compose.override.yml` | `/opt/mailcow-dockerized/docker-compose.override.yml` | `644 root:root` |
| `haproxy.cfg` | `/opt/mailcow-dockerized/data/conf/matemail-gateway/haproxy.cfg` | `644 root:root` |
| `postfix-extra.cf` | `/opt/mailcow-dockerized/data/conf/postfix/extra.cf` | `644 root:root` |
| `../../scripts/postfix_policy_bridge.py` | `/opt/mailcow-dockerized/data/conf/matemail-gateway/postfix_policy_bridge.py` | `644 root:root` |
| `certbot-deploy-hook-mailcow-mx.sh` | `/etc/letsencrypt/renewal-hooks/deploy/mailcow-mx.sh` | `750 root:root` |
| `nginx-mx.matemail.online.conf` | `/etc/nginx/sites-available/mx.matemail.online` (symlinked into `sites-enabled/`) | `644 root:root` |
| `vars.local.inc.php` | `/opt/mailcow-dockerized/data/web/inc/vars.local.inc.php` | `644 root:root` |

None contains a secret. Nothing in this directory ever should.

### What is deliberately NOT here

| Not versioned | Why |
|---|---|
| `mailcow.conf` | carries the engine database password and other generated secrets |
| `/root/.mailcow-api-key`, `/root/.mailcow-admin-credential` | credentials, root-only on the server |
| TLS certificates and private keys | issued per host by Certbot; a private key must never enter a repository |
| Engine database state, mail data, DKIM keys | data, and the DKIM private keys are the thing DEC-007r exists to keep inside the engine |
| Validation and diagnostic scripts on the server | the procedures are documented below; the repository holds tests, not ad-hoc tooling |

### Why these five and not more

Each one is configuration whose **loss would materially harm recovery**, and
none is regenerable from anything else:

- the two gateway files **are** MateMail's only path to the engine;
- without the Certbot hook, renewed certificates never reach the engine and
  mail TLS silently expires within 90 days;
- without the nginx vhost, the certificate cannot be issued or renewed at all
  (the ACME HTTP-01 challenge has nowhere to land);
- `vars.local.inc.php` is a one-line security control — losing it re-enables
  private DKIM key exposure through the engine's API, which is exactly the
  thing DEC-007r forbids.

Everything else on the server is either secret-bearing, regenerated by mailcow
itself, or host-specific.


**Gateway image:** `haproxy:3.2.23-alpine`, pinned by digest

## Why it is built this way

### Why a gateway at all

The engine's ports were originally published on MateMail's own Docker bridge
gateway, `172.24.0.1`. That was measured and rejected: **a published bind
address selects a destination address, it never restricts the source.** Six
unrelated application networks on this host — NetaMate, MateDesk, MateAssist,
MateConnect, the portfolio stack and the default bridge — could all open TCP
connections to the engine's API and submission ports.

`docker-proxy` holds a userland socket on that address and accepts on it
whichever bridge the traffic arrives from. Rule counters confirmed the DNAT rule
never fired during the test, so the traffic does not traverse `DOCKER-USER` and
a rule there would not have helped.

The fix removes the socket rather than filtering it.

### Why HAProxy

A small, well-understood TCP proxy with a configuration short enough to read in
one sitting. `nginx-mailcow` was evaluated first and cannot do it update-safely:
its image has nginx's stream module compiled in, but the only writable,
bind-mounted nginx path is `/etc/nginx/conf.d`, which upstream includes *inside*
`http {}` where `stream {}` is invalid — and the one file with a top-level
context, `nginx.conf.j2`, is tracked in mailcow's git and restored by
`update.sh`.

### Why TCP passthrough and not a protocol-aware proxy

The gateway is layer 4. It does not terminate, inspect or re-originate TLS, and
it is not an SMTP relay.

That is what keeps certificate verification meaningful: the certificate MateMail
validates is the real one presented by nginx and by Postfix, for the real
hostname it dialled. A terminating proxy would have to hold key material and
MateMail would be validating the gateway rather than the engine.

### Why one gateway owns `mx.matemail.online`

MateMail addresses the engine as `mx.matemail.online` for both HTTPS and SMTP,
and its certificate is issued for that name.

Attaching `nginx-mailcow` and `postfix-mailcow` to the link under the same alias
would let Docker's DNS return either address — while 8453 exists only on one and
587 only on the other. That is a routing coin-flip. One ingress owning the name
makes the destination deterministic.

### Why no host ports are published

Publishing one would rebuild the exact hole this replaces. The gateway is
reachable only from `matemail_engine_link`, and the engine's own ports stay on
`127.0.0.1` for operator access over an SSH tunnel.

### Why the override file rather than editing mailcow's compose

`docker-compose.override.yml` is mailcow's supported extension point and is
listed in its own `.gitignore`, so `update.sh` leaves it alone. Upstream's
`docker-compose.yml` is replaced wholesale on every upgrade — a local edit there
would be reverted silently at the worst possible moment.

## The dedicated network

```bash
docker network create --internal matemail_engine_link
```

Created **once, by hand**, and owned outside both Compose projects so neither
`docker compose down` can delete a network the other still depends on.

`--internal` is not optional. Without it Docker creates a routable bridge, and a
routable engine link silently restores the cross-application exposure this whole
design exists to remove.

Verify:

```bash
docker network inspect matemail_engine_link \
  --format '{{.Name}} internal={{.Internal}}'
# matemail_engine_link internal=true
```

**MateMail's deployment does not create this network.** It verifies that the
network exists and that `Internal=true`, and refuses to deploy otherwise. That
is deliberate: a network conjured mid-deploy would get Docker's defaults, which
means routable.

No subnet is pinned. Docker allocates one, and nothing depends on which.

## The static `10.244.0.247` address — check this before every engine upgrade

The gateway holds a fixed address on the engine's own network because the
engine's API ACL is scoped to it:

```
allow_from = 10.244.0.247
skip_ip_check = 0
```

The gateway originates the API connection, so the engine observes the gateway
and nothing else. Scoping the ACL to a DHCP address would lock MateMail out of
its own mail engine the first time containers were recreated in a different
order.

`.247` was chosen because mailcow `2026-07b` assigns its own infrastructure
statics at `.248` (sogo), `.249` (redis), `.250` (dovecot), `.253` (postfix) and
`.254` (unbound), and dynamic allocation runs upward from `.2`. It was verified
free against the live network.

### ⚠ This is not guaranteed to stay free

**Before every mailcow upgrade, check that the new release has not claimed
`.247` for a new upstream service:**

```bash
cd /opt/mailcow-dockerized
git show <new-tag>:docker-compose.yml | grep -n ipv4_address
```

If the new release claims `.247`:

1. **STOP.** Do not start the upgraded stack.
2. Pick a new address, verified free against both the new release's statics and
   the live network.
3. Update `ipv4_address` in `docker-compose.override.yml`.
4. Update `allow_from` in the engine's `api` table to the new address.
5. Re-run the isolation and TLS validation below before considering the upgrade
   done.

A silent collision presents as the gateway failing to start, or — worse — as the
gateway starting on a different address and every MateMail API call being
refused by an ACL that no longer matches.

## The SMTP policy bridge (P5)

### What it is

Postfix cannot call an HTTP API. It speaks the `check_policy_service` protocol —
`key=value` lines over a socket, answered with one `action=` line — so something
has to translate. `scripts/postfix_policy_bridge.py` is that translation and
nothing else: every decision it relays comes from MateMail, and it holds no
policy of its own.

It runs as a sidecar in the engine's Compose project, on the engine network at
`10.244.0.246:10031` and on `matemail_engine_link`, so it can reach the MateMail
backend by service name. **No host port is published**, for exactly the reason
the gateway publishes none — see "Why no host ports are published" above. This
socket decides whether mail may be sent; a published one would be reachable from
every other Docker network on the host.

An earlier design ran the bridge on the host and opened a firewall hole for the
Docker subnet. That is the arrangement DEC-014 measured and rejected, and its
systemd unit has been deleted rather than left in the repository beside the
replacement.

### Where it hooks into Postfix

`postfix-extra.cf` is installed as mailcow's `extra.cf`, which its `postfix.sh`
appends to the generated `main.cf` on every start. Postfix takes the last
definition of a parameter, so this overrides without editing a file that is
regenerated on upgrade.

Two hooks, at two stages, for two different reasons:

| Parameter | Fires | MateMail is asked | Counts? |
|---|---|---|---|
| `smtpd_recipient_restrictions` | once per RCPT TO | `stage=rcpt` | no |
| `smtpd_end_of_data_restrictions` | once per message | `stage=end_of_data` | yes |

**Ordering in the recipient chain is the entire point.** The hook sits *after*
`permit_mynetworks` and *before* `permit_sasl_authenticated`:

- after `permit_sasl_authenticated`, Postfix stops evaluating the moment a
  client authenticates, so every authenticated submission — the traffic MateMail
  exists to rule on — would short-circuit before reaching the hook. Installed,
  running, and never asked;
- before `permit_mynetworks`, the engine's own unauthenticated injections
  (watchdog probes, quarantine digests) would be put to customer policy, which
  knows nothing about their recipients and would refuse them.

The end-of-data list has no permit in front of it, so every message reaches
MateMail there — including the platform sender's, which the recipient hook lets
past via mynetworks.

### Why the bridge answers DUNNO and never OK

In Postfix, a policy service answering `OK` means *permit and stop evaluating
this list*. The entry after ours is `reject_unauth_destination` — the check that
stops MateMail relaying for domains it does not host. `OK` would skip it.

`DUNNO` means "no objection, carry on", leaving every later restriction in
force. There is a test asserting no code path can emit `OK`.

### Failure behaviour

If MateMail cannot be reached, or the shared secret is wrong, the bridge answers
`DEFER_IF_PERMIT` — never `DUNNO`. Mail is retried rather than sent unchecked.

`DEFER_IF_PERMIT` rather than a bare `DEFER` so a relay attempt that a later
restriction would reject outright is still rejected, instead of being softened
into a retryable 4xx during an outage.

**This makes MateMail's availability part of the mail path.** Once installed,
MateMail being down means mail stops flowing — temporarily and retryably —
rather than flowing unmetered. That is the intended trade, and it is worth
knowing before you install it rather than after.

### The shared secret

The bridge authenticates to MateMail with `INTERNAL_API_SECRET`. It must be set
in the engine's `mailcow.conf` as:

```
MATEMAIL_INTERNAL_API_SECRET=<the same value as MateMail's INTERNAL_API_SECRET>
```

It is required, not defaulted: the Compose service uses `${VAR:?}` so the stack
refuses to start rather than starting a bridge that defers every message.
`mailcow.conf` is not versioned here — it carries the engine database password.

### Installing it

Use `scripts/install-policy-bridge.sh`, which backs up what it replaces,
refuses to run without the secret, checks that the address Postfix dials is the
address Compose binds, starts the bridge *before* reloading Postfix, and ends by
printing the engine's effective configuration.

```bash
sudo bash scripts/install-policy-bridge.sh --check    # verify, change nothing
sudo bash scripts/install-policy-bridge.sh            # install
```

### Verifying it afterwards

```bash
cd /opt/mailcow-dockerized
docker compose exec -T postfix-mailcow postconf \
    smtpd_recipient_restrictions smtpd_end_of_data_restrictions
```

`check_policy_service` must appear **before** `permit_sasl_authenticated`. If it
does not, mail is not being checked.

### ⚠ Re-validate after every mailcow upgrade

`postfix-extra.cf` reproduces part of an upstream-generated restriction chain.
An upgrade that changes that chain upstream leaves this override silently pinned
to the old list — keeping our hook, and also keeping whatever upstream decided
to change.

`backend/tests/test_engine_policy_integration.py` holds the upstream chain this
was derived from and fails if the two diverge, so the divergence surfaces in CI.
After any upgrade:

1. read the newly generated `data/conf/postfix/main.cf`;
2. update `UPSTREAM_RECIPIENT_CHAIN` in that test;
3. re-derive `postfix-extra.cf` from it;
4. re-run `install-policy-bridge.sh` and check the `postconf` output again.

The static address `10.244.0.246` needs the same check as the gateway's `.247` —
see "The static `10.244.0.247` address" above.

## Installing or updating

```bash
# 1. the network must already exist (see above)
docker network inspect matemail_engine_link --format '{{.Internal}}'   # true

# 2. place the two files
install -o root -g root -m 644 docker-compose.override.yml \
  /opt/mailcow-dockerized/docker-compose.override.yml
install -d -o root -g root -m 755 /opt/mailcow-dockerized/data/conf/matemail-gateway
install -o root -g root -m 644 haproxy.cfg \
  /opt/mailcow-dockerized/data/conf/matemail-gateway/haproxy.cfg

# 3. check the HAProxy config before anything restarts
docker run --rm -v /opt/mailcow-dockerized/data/conf/matemail-gateway/haproxy.cfg:/tmp/h.cfg:ro \
  haproxy:3.2.23-alpine haproxy -c -f /tmp/h.cfg

# 4. validate the merged Compose, then start ONLY the gateway
cd /opt/mailcow-dockerized
docker compose config --quiet
docker compose up -d --no-deps matemail-engine-gateway
```

### The three host-side files

Independent of the gateway, and each needed for a different reason.

```bash
# DKIM private-key display OFF. Must exist before the engine serves any API
# request, and it is `vars.local.inc.php` — NOT vars.inc.php, which upstream
# replaces on update, and NOT a mailcow.conf variable, which the engine never
# reads for this setting.
install -o root -g root -m 644 vars.local.inc.php \
  /opt/mailcow-dockerized/data/web/inc/vars.local.inc.php
cd /opt/mailcow-dockerized && docker compose restart php-fpm-mailcow

# ACME challenge vhost — without it the certificate cannot be issued or renewed.
install -o root -g root -m 644 nginx-mx.matemail.online.conf \
  /etc/nginx/sites-available/mx.matemail.online
ln -sfn /etc/nginx/sites-available/mx.matemail.online \
        /etc/nginx/sites-enabled/mx.matemail.online
nginx -t && systemctl reload nginx     # never reload without a passing -t

# Certbot deploy hook — without it, renewals never reach the engine and mail
# TLS silently expires within 90 days.
install -o root -g root -m 750 certbot-deploy-hook-mailcow-mx.sh \
  /etc/letsencrypt/renewal-hooks/deploy/mailcow-mx.sh
```

Verify the DKIM control from the **running** PHP environment rather than from
the file — the file is not proof that the engine read it:

```bash
docker compose exec -T php-fpm-mailcow php -r \
  'require "/web/inc/vars.inc.php"; @include "/web/inc/vars.local.inc.php";
   var_dump($SHOW_DKIM_PRIV_KEYS === false);'
# bool(true)
```

Exercise the certificate hook rather than trusting it, by running it the way
Certbot will:

```bash
RENEWED_LINEAGE=/etc/letsencrypt/live/mx.matemail.online \
  /etc/letsencrypt/renewal-hooks/deploy/mailcow-mx.sh
```

Never `docker compose up -d` the whole stack to apply a gateway change — that
recreates services whose configuration did not change.

## Validating

```bash
# gateway healthy, everything else untouched
cd /opt/mailcow-dockerized
docker compose ps matemail-engine-gateway
docker compose ps --format '{{.Service}} {{.State}} {{.Health}}' | grep -Ei 'unhealthy|restarting'

# addresses and alias
docker inspect mailcowdockerized-matemail-engine-gateway-1 \
  --format '{{range $k, $v := .NetworkSettings.Networks}}{{$k}} {{$v.IPAddress}} {{$v.Aliases}}{{println}}{{end}}'

# no host port may appear for the gateway
docker compose ps matemail-engine-gateway --format '{{.Ports}}'
```

Then, from a disposable container on the link using MateMail's own backend
image, confirm: `mx.matemail.online` resolves to exactly one address; HTTPS 8453
completes a TLS handshake with hostname verification; SMTP 587 completes
STARTTLS with hostname verification; and both present the real
`mx.matemail.online` certificate. **No AUTH, no mail.**

Finally re-run the negative test: from every *other* Docker network on the host,
both ports must be unreachable. That is the gate — the control passing is not
enough on its own.

## Rolling back

```bash
cd /opt/mailcow-dockerized
docker compose rm -sf matemail-engine-gateway
mv docker-compose.override.yml /root/            # keep it; do not delete
docker compose up -d
```

Reverting leaves MateMail with no path to the engine, so it is only correct
alongside reverting MateMail to a release that does not expect one. Do **not**
restore the old host-published bindings as a shortcut: that reopens the
cross-application exposure.

The full incident runbook, including what to do when the network has been
deleted, is on the server at `/root/matemail-p4b-ROLLBACK.md`.

## Upgrading the gateway image

Pinned by tag **and** digest. To move to a newer HAProxy point release:

1. Confirm the branch is still long-term supported at
   <https://www.haproxy.org/> — do not assume from the version number.
2. `docker pull haproxy:<new>-alpine`, then read its digest with
   `docker image inspect ... --format '{{index .RepoDigests 0}}'`.
3. Update both the tag and the digest in `docker-compose.override.yml`.
4. Recreate that one service and re-run the validation above.

Never switch to a floating tag. This process sits in the path of customer mail.
